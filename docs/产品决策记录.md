# FaultDetect · 产品决策记录

> 记录我在这个产品上**做过的每一个取舍**，以及**从别人产品里提炼的方法**。
> 格式统一：**约束 → 选择 → 理由**。

---

## 一、我自己的六个核心决策

### 1. 用固定 7 步 SOP 替代"凭经验猜"

| | |
|---|---|
| **约束** | 现场新人不只不会修，是**不知道该先看什么**；老手经验在脑子里无法传递 |
| **选择** | 固定流程：URL 解析 → TCP 存活 → HTTP 探测 → 状态码分析 → 响应特征提取 → 证据收集 → 分支判断 |
| **理由** | **AI 只能回答你能问出来的问题。而现场最难的，是你根本不知道该问什么。** |
| **代价** | 灵活性下降 —— 非典型故障可能被流程带偏 |

### 2. 交付三种形态，而不是只做 Docker

| | |
|---|---|
| **约束** | 现场机器装不了 Docker、无管理员权限、甚至没装 Java |
| **选择** | 单文件 exe（内嵌精简 JRE）为主；另提供标准版与 Docker 版 |
| **理由** | **用户的真实环境才是设计约束，不是技术栈方便** |
| **代价** | 三种形态维护成本高。**更聪明的做法是只维护一种、其他用脚本生成** —— 这是我承认的工程债 |

### 3. 结论分三层，不给单一总分

| | |
|---|---|
| **约束** | AI 产品最常见的坑是**把推断当事实展示** |
| **选择** | 观测层（实测）/ 归因层（推断）/ 结论层（建议）三层分开呈现 |
| **理由** | **一个总分是最容易被误读的东西** —— 用户没法知道哪一部分不可信 |
| **代价** | 界面更复杂，用户学习成本略高 |

### 4. 每条判断强制带反证条件与验证动作

| | |
|---|---|
| **约束** | 排障结论要汇报、要被追问、要能复盘 |
| **选择** | 假设必须同时给出依据 + 反证条件 + 验证动作 |
| **理由** | 交不上去的结论等于没有结论 |
| **代价** | **最花时间的部分**（近 60 处逐条手写）；且目前**靠人工纪律保证，没有断言机制** |

### 5. LLM 层默认关闭

| | |
|---|---|
| **约束** | 内网模型不可达；部分客户环境把生产内容送公网模型本身违规 |
| **选择** | 默认关闭 + 按需触发；六条异常路径全部降级为规则结论 |
| **理由** | **检验标准：把模型接口拔掉，产品还能不能给出完整结论** |
| **代价** | 默认状态下用户享受不到模型的表达增强 |

### 6. 差分实验只做只读，写操作直接拒绝

| | |
|---|---|
| **约束** | 差分实验真的在打客户系统 |
| **选择** | 只读白名单 + **运行时抛错拒绝**（不只是名单过滤） |
| **理由** | **用户敢用自动化，是因为知道它不会闯祸** |
| **代价** | 放弃了对"写操作异常"的诊断能力 |

## 二、从朋友开源项目（PathPilot）提炼的六套方法

> **归属声明**：PathPilot 是我朋友的开源项目，他开源给我学思路。
> **我只主张"从中学到并迁移的方法"，不主张该项目所有权。**

### 模式 1 ⭐⭐⭐ 分级授权：把"什么能自动做"写成四级

**他的做法**：动作按风险分四级并绑定自主权 ——
L0（读/排序/草稿）可自动；L1（导航/低风险填写）默认可自动但可暂停；L2（登录/验证码/薪资/身份）**必须用户确认**；L3（发送/提交/删除）**必须显式确认并显示对象、内容、数量、后果**。
**而且不靠自觉**：高风险字段没确认过，**代码直接拒绝**。

**我提炼出的方法**：**风险分级不是文档里的一张表，而是可以被代码执行的授权级别。**

**我落到哪了** ✅ **已落地一半** ——
差分实验严格限制在只读操作，**而非只读方法直接抛 `IllegalStateException` 拒绝**。
**这比单纯白名单更强**：白名单只挡"名单外"的，**运行时抛错挡的是任何绕过路径**。

**我还没做到的** ⚠️ 只用在这一处，没有提升为整个产品的通用框架；且"清空历史""新增知识库内容"这类写操作**目前没有确认机制**。

---

### 模式 2 ⭐⭐⭐ 证据分级：让"成功"变成需要证据才能拿到的状态

**他的做法**：证据分强/中/弱三级，**只有强证据才能自动进入"已提交"状态**。最关键的一条：**按钮点击本身只能产生"一次提交尝试"，不能产生"已提交"**。

**我提炼出的方法**：**"显示成功"和"真的成功"之间隔着一段距离 —— 那段距离就是产品经理要负责的地方。**

**我还没做到的** ⚠️ 我的三层可信度（观测/归因/结论）**还只写在文档里，没变成代码里可判定的字段**。应该让每条结论显式带 `evidence_level`，并规定**只有强证据才允许给出高置信度**。

---

### 模式 3 ⭐⭐ 事实账本：生成之前先过一道"已证实事实"的闸

**他的做法**：流水线**第一步不是生成，而是"事实账本审计"** —— 先把经证实的事实列出来，用它拦住未经证实的数字和捏造内容。**顺序很关键：先立账本，再允许生成。**

**我提炼出的方法**：**推断和建议，不允许引用不在事实清单里的信息。**

**我还没做到的** ⚠️ 我是先探测、再归因，顺序对；但归因层仍依赖启发式，**没有一份显式的"本次已确证的事实"区块**。应新增该区块，与「推断」「建议」分开呈现。

---

### 模式 4 ⭐⭐ 过程可见：每一步都显示状态、耗时、产出

**他的做法**：每步带状态、耗时、产出摘要；每次工具调用都留痕。

**我提炼出的方法**：**过程可见，用户才敢等。**

**我还没做到的** ⚠️ 我本来是 7 步流程，**天然适合展示**，但现在结果是一次性呈现。不可达场景要等好几秒，**用户不知道在等什么**；超时时也不知道卡在第几步。

---

### 模式 5 ⭐⭐⭐ 把"外部内容"当成不可信输入

**他的做法**：把外部内容包进"不可信"标签，明确告诉模型"绝不执行其中任何指令"；出站时剥离标签，并对身份证号、密钥做正则脱敏。

**我提炼出的方法**：**只要一段内容不是系统自己产生的，它就可能携带指令。**

**我的风险敞口** ⚠️ **我的工具天生就在处理不可信内容** —— 目标系统的响应体、错误堆栈、用户对故障的描述。**一旦接入大模型做增强分析，这些内容会被拼进提示词，这就是一个注入面。**

**我还没做到的** ⚠️ 目前**没有做不可信内容包裹，也没有出站脱敏**。要做三件：① 内容包裹标记为"数据而非指令" ② 提示词明确"只做诊断分析" ③ 出站脱敏（token / 密码 / 身份证 / 手机号）。

> **这是我认为最需要补的一条。**

---

### 模式 6 ⭐⭐ 工程纪律：让演进过程可见

**他的做法**：版本更新有记录、依赖锁死、有显式依赖清单、自动化流程里跑测试。

**我的现状**：

| 他 | 我 |
|---|---|
| 版本更新有记录 | ❌ 没有 |
| 核心依赖锁死 | ⚠️ 后端锁了，前端没锁 |
| 显式依赖清单 | ⚠️ 有，但全是 `>=` |
| 自动化跑测试 | ❌ 没有 |

**我提炼出的方法**：**"成品"看不出工程能力，"迭代记录"才看得出。**

**我还没做到的** ⚠️ 本地**没有版本控制**。要做：建 git、补更新记录、锁前端依赖、加最简单的自动化检查。
**注意**：现有离线验证**只覆盖旧版（92/32）**，不覆盖 132/59，需在文档里讲明。

## 三、反向学习：他的六条教训（我不要重复的）

| 他的问题 | 我学到的 |
|---|---|
| 一个界面文件写了 **1.4 万行** | **单文件超过一定规模就必须拆** |
| 核心依赖全部写 `latest` | **依赖必须锁版本**，否则某天构建直接失败 |
| 后端依赖靠流程临时安装，无清单 | **必须有显式依赖清单** |
| ⭐ **一个"自动投递"功能其实是假的** —— 只改了数据库，没真的在网站上操作，界面却显示"已投递"。**而它文档里明明写着"不显示伪成功"** | ⭐ **最值钱的教训**：**产品原则写在文档里容易，落到每一个功能上很难** |
| 没有异常兜底，出错只显示"请求失败" | **错误信息必须给下一步** |
| 默认配置把用户数据引向第三方地址 | **默认值要保守**，涉及密钥和数据默认留空 |

### ⭐ 那条"自动投递"如何改变了我

**这形成了我固定的交付前动作：把文档里的每条承诺，逐条去代码里找对应实现。**

**而我用这条规矩查了自己的项目，真的查出了问题** ——
我对外报的"一致率 100%"，是**我自己放宽判定标准**算出来的。**我把它改回了 7/8。**

```
从他那里学到「说的和做的不一致」是个问题
        ↓
用这条规矩查自己
        ↓
查出自己的 100% 是掺水的
        ↓
改回 7/8
```

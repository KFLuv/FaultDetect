# FaultDetect · 现场排障 AI 诊断系统

> **产品定位**：面向现场实施与运维人员的排障工具
> **我的角色**：产品设计 · 迭代 · 评测（自有项目）
> **源码**：https://github.com/KFLuv/fault-detect-system
> **状态**：✅ 已上线可用（Java 版 v2.0）

---

## 一句话

**输入一个故障 URL，自动跑完 7 步排障 SOP，输出可直接汇报的 3 段式诊断报告，并附本次故障的手动排查教学。**

**核心设计目标：让"我查出来是这个问题"可被验证、可被复核。**

---

## 产品定位：为什么不是"问 AI 就行"

> **"AI 只能推理你转述的事实。用户说'网站打不开'，可能是前端、也可能是网关或数据库 —— 转述那一秒，事实就丢了。我的产品自己去现场把事实拿回来。"**

| 层次 | 通用 AI 聊天 | FaultDetect |
|---|---|---|
| **信息层** | 只能推理你**转述**的事实 | **自己去现场取事实**（状态码、响应体、连通性、耗时） |
| **可信层** | 给 5 个"可能原因"，每次还不一样，不能审计 | 结论带**反证条件与验证动作**，有**独立真值自检** |
| **合规层** | 把内网内容贴给公网模型可能违规 | **本地运行**，数据不出门 |

| | |
|---|---|
| **主用户** | 现场实施人员 / 运维人员（非资深） |
| **典型场景** | 客户报"系统打不开 / 很慢 / 报错"，现场人员需要在**几分钟内**给出一个**能汇报上去**的判断 |

## 核心产品决策

> 每条都是 **约束 → 选择 → 理由**。

### 决策 1 · 把老手的排查顺序固化成 7 步 SOP

| | |
|---|---|
| **约束** | 现场新人凭感觉试，反复试错；老手经验在脑子里，无法传递 |
| **选择** | 固定 7 步流程：URL 解析 → TCP 存活 → HTTP 探测 → 状态码分析 → 响应特征提取 → 证据收集 → 分支判断 |
| **理由** | AI 只能回答**你能问出来的问题**。现场最难的是**你根本不知道该问什么**。流程解决的就是这个 |
| **附加设计** | 结果里**额外附一段"这一次该怎么手动排查"的教学** —— 所以它不是搜索引擎，是**教练** |

### 决策 2 · 三种交付形态，按现场环境适配

| | |
|---|---|
| **约束** | 现场机器**装不了 Docker**、没有管理员权限、**甚至没装 Java** |
| **选择** | **主推单文件 exe**（内嵌精简 JRE，目标机免装 Java）；另提供标准版与 Docker 版 |
| **理由** | **用户的真实环境才是设计约束，不是"我们技术栈方便"**。三种形态**功能完全一样**，区别只在适配什么环境 |
| **踩过的坑** | `jlink` 打包精简 JRE 时**必须带上 `jdk.crypto.ec` 模块**，少这一个 HTTPS 握手直接失败。**这个坑只能在真机上试才会发现** |

### 决策 3 · 结论分三层展示，不给单一总分

| | |
|---|---|
| **约束** | AI 产品最常见的坑：**把推断当事实展示**。用户看到笃定的文字，以为是实测结果 |
| **选择** | **观测层**（我实测到的：状态码/耗时/响应体）· **归因层**（我推的，启发式）· **结论层**（建议，带置信度）。**三层在界面上长得不一样** |
| **理由** | 用户需要完整信息才能判断，所以**拆的是视觉层级，不是页面**。**一个总分是最容易被误读的东西** —— 宁可给计数与清单，也不给一个 88 分 |

### 决策 4 · 每条判断强制带「依据 + 反证条件 + 验证动作」

| | |
|---|---|
| **约束** | 排障结论要**汇报上去、要被追问、要能复盘**。交不上去的结论等于没有结论 |
| **选择** | 每条假设同时给出三样：**依据**（命中了什么）· **反证条件**（什么情况下这条不成立）· **验证动作**（去哪、怎么自己核一遍） |
| **理由** | 大多数人只会说"我认为是数据库问题"。会说"**我认为是 X，如果 Y 出现那就不成立，请你去 Z 核对**" —— 这是产品经理和执行者的分界线 |
| **规模** | 代码里 `refute` / `verify` 调用合计接近 60 处，对外报 **52 条约束规则** |

**真实例子（可直接引用）：**
> **假设**：「数据库单行查询返回了多行」
> - **依据**：响应关键信息摘要
> - **反证条件**：*"直接在数据库执行同一条查询只返回 1 行 → 问题不在这条 SQL，而在上层调用逻辑"*
> - **验证动作**：*"去掉 limit 执行该查询，确认实际返回行数"*

### 决策 5 · LLM 增强层默认关闭，异常全部降级

| | |
|---|---|
| **约束** | ① 内网离线环境模型不可达 ② 很多客户环境**把生产内容贴给公网模型本身就是违规** |
| **选择** | LLM 层**默认关闭、按需触发**；六条异常路径**全部降级为规则结论**；状态记为 `degraded`，原因原样写进结果 |
| **理由** | **检验标准只有一条：把模型接口拔掉，产品还能不能给出完整结论？** 能 → 价值是自持的；不能 → 它就是个壳子 |
| **六条异常路径** | 非 2xx / 连接超时 DNS 证书错误 / 解析异常 / 非法 JSON / 缺字段 / 找不到预期结构 |

### 决策 6 · 差分隔离实验只做只读，写操作当场拒绝

| | |
|---|---|
| **约束** | 差分实验是**真的在打客户的系统**，一不小心会造成影响 |
| **选择** | 只读白名单（GET / HEAD）+ **运行时硬性拒绝**：发现是写动作**直接抛错停下**，不给绕过名单的机会 |
| **理由** | **用户敢用自动化，不是因为它功能多，而是因为知道它不会闯祸。** 先定义红线，再定义功能 |

### 独立真值自检（8 条用例）

**核心原则：不允许用生成方自己验证自己。**

| | 实现 |
|---|---|
| **真值** | `java.net.HttpURLConnection`（显式 `Proxy.NO_PROXY`）—— 与主检测链路**完全独立** |
| **被测** | `java.net.http.HttpClient` |
| **自包含** | 内置极简测试服务，**随机端口、仅绑 127.0.0.1、跑完即关** |
| **只读安全** | 全部 GET 请求 |

**8 条用例：**

| 用例 | 场景 | 结果 |
|---|---|---|
| SC_01 | 本地 200（UTF-8 中文响应） | 一致 |
| SC_02 | 本地 404 | 一致 |
| SC_03 | 本地 500（响应含异常类名） | 一致 |
| SC_04 | GBK 响应（**响应头声明** charset） | 一致 + 中文未乱码 |
| SC_05 | GBK 响应（**响应头未声明** charset，需回退探测） | 一致 + 中文未乱码 |
| SC_06 | 服务端挂起不响应 | 一致 |
| SC_07 | 端口无人监听 | 一致 |
| SC_08 | 域名无法解析 | **不一致（已声明）** |

### ⭐ 当前口径：8 条用例，**7 项一致 + 1 条已声明的粒度差异**

**这个数字我改过一次，先说清楚原因：**

我一度对外报"**8/8，一致率 100%**"。后来复盘发现：**那唯一一条不一致，是我自己在判定标准里把它归成了"同类"才算过的。**

- 真值：**DNS 解析失败**
- 系统归入：**"连接被拒绝 / 网络不通"**
- **层次判断是对的**（都是"网络不可达"），**但粒度不够**（没细分 DNS 和端口）

**放宽标准算出来的 100% 不能当证据。所以我改成报 7/8，并说明差的那一条差在哪。**

代码里保留了那个归类（运行上它是合理的同族处理），但注释写明"不掩盖该差异"，界面上用黄字如实标注。

## 两个真实现场问题（误判修复）

> 这两个问题**只能在真跑生产环境时遇到，看教程永远学不到**。

### 问题 1 · h2c 被网关吊住连接

| | |
|---|---|
| **现象** | 所有 HTTP 检测都超时。用户报"网站很慢" |
| **排查** | 连接建上了、请求发出去了、**就是没有任何响应，一直等到超时** |
| **真因** | JDK 的 HttpClient 默认用 HTTP/2，对明文 `http://` 会先发 **h2c 协议升级握手**。而很多网关对不认识的 Upgrade 请求**既不回 101 也不忽略，直接把连接吊住** |
| **修复** | 显式强制 HTTP/1.1 |
| **关键** | **表象是"服务器慢"，真因在协议协商层** |

### 问题 2 · GBK 编码致关键词匹配全失效

| | |
|---|---|
| **现象** | 系统给出的归因完全错误 |
| **真因** | 系统按固定编码解码响应体，**忽略响应头 charset**。老内网系统常用 GBK → 中文异常信息变乱码 → **关键词匹配全部失败** |
| **修复** | 按字节接收 + 依响应头 charset 解码，**并补回归用例**（SC_04 / SC_05 覆盖两条解码路径） |
| **关键** | 这不是"查不出来"，是"**查错了**" —— **比查不出来更危险，因为它会让人直接信** |

## 我在这个产品上还没做到的

> **一个产品最大的问题是它自己不知道的问题。所以这一节我主动写。**

| # | 缺什么 | 影响 |
|---|---|---|
| **1** | **入门门槛太高，等于砍掉一半目标用户** | 用户要先用浏览器开发者工具**找到接口地址和 Token** 才能开始检测 —— 而"不知道该看哪里"恰恰是这个产品要解决的痛点。**会翻开发者工具的人，离直接问 AI 只差一步。** 下一步要补：**浏览器书签脚本**（在故障页面点一下自动抓现场信息） |
| **2** | **三态判定靠人工纪律，不靠机制** | `refute_if` / `verify_actions` 字段**没有非空断言**。应该加断言，让"缺反证条件"变成**启动期错误** |
| **3** | **安全没做收尾** | 主检测链路 TLS 是 trust-all，**没有 SSRF 防护**（无内网/回环地址黑名单），**无鉴权**。离线单机场景可接受，**服务化部署前必须先补** |
| **4** | **旧版（Python v1）与新版（Java v2.0）能力不对等** | Python 版（92 场景 / 32 状态码）**没有自检、没有差分实验、没有假设引擎、没有 LLM 层**。所以不能说"两版功能相同" |

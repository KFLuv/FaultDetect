# FaultDetect 1.3.0 到 1.3.8 产品迭代脉络

更新日期：2026-11-08

## 这一串版本到底在做什么

从 1.3.0 开始，迭代主线不是不断增加通用 AI 功能，而是把 FaultDetect 从“能跑诊断的页面”逐步做成一套真实现场可用的 Web HTTP 排障工作台：

```text
桌面可运行
  -> 断线能恢复
  -> 业务人员不用 F12 就能采集
  -> 采集体验收进主窗口
  -> 真实网站可用
  -> 不可重放请求也能交接
  -> 请求体和 Trace 证据补齐
  -> 场景与测试可靠性修复
  -> 能力边界和适配范围完整呈现
```

这 8 个版本实际上补的是四条不同的产品链路：

| 产品链路 | 对应版本 | 结果 |
| --- | --- | --- |
| 交付可用 | 1.3.0、1.3.1 | 双击可运行，后端断开能自动恢复 |
| 现场可用 | 1.3.2、1.3.3、1.3.4 | 业务人员不需要 F12，采集收进主窗口，真实网站可操作 |
| 证据可用 | 1.3.5、1.3.6 | 不可重放请求有快照，请求体、Trace 和错误降级补齐 |
| 可信可用 | 1.3.7、1.3.8 | 修复数据与回归问题，并把能力、场景和边界完整暴露 |

| 版本 | 核心变化 | 解决的问题 |
| --- | --- | --- |
| 1.3.0 | Electron 桌面端、内嵌 JRE、自动启动后端、单实例 | 现场目标机不需要 Java、Node 和浏览器，产品从网页工具变成桌面工具 |
| 1.3.1 | 后端断线自动重启和请求重试 | 修复 `fail to fetch`，后端意外退出后不再要求用户手动重启 |
| 1.3.2 | 内置采集助手、记录开关、按钮请求关联、内置教学网站 | 业务人员不必打开 F12 找 URL、Cookie 和接口 |
| 1.3.3 | 采集收进主窗口、原生剪贴板、结果按需展开 | 去掉独立采集窗口和浏览器剪贴板权限，现场操作更稳定 |
| 1.3.4 | 三个真实业务教学页面、LTing / SauceDemo / 公共 500 页面验证 | 证明内置窗口不是只能打开自制演示页 |
| 1.3.5 | POST / 审批 / 提交类请求失败快照 | 不可重放请求也能保留状态、响应、Trace、耗时和交接信息 |
| 1.3.6 | 请求体确认采集与脱敏、Trace 日志模板、企业环境错误降级 | 补齐 POST 参数证据、日志入口和加载失败提示 |
| 1.3.7 | 未知场景归档幂等、状态码搜索、恢复测试修复 | 修复数据和测试可靠性问题，补齐状态码查询 |
| 1.3.8 | 完整能力矩阵、完整适配边界、132 个场景动态目录 | 让用户明确产品能做什么、不能做什么，以及当前知识库到底覆盖哪些场景 |

## 产品现在处在什么阶段

FaultDetect 现在不是“输入 URL 就自动修好系统”的工具，而是：

> **现场第一响应 + 请求证据采集 + 只读 HTTP 检测 + 分层归因 + 研发交接。**

它最适合：

- 业务系统报错，但不知道是前端、接口、服务、网关、权限还是数据库；
- 业务人员只会复现问题，不会用 F12；
- 需要把现象、请求、状态、Trace 和排查动作完整交给研发；
- 内网或生产环境不能把数据直接交给公网大模型；
- 需要先做只读、可审计的第一轮排查。

## 当前最重要的能力

- 不需要 F12，在主窗口里复现一次问题；
- 按钮动作与失败请求自动关联；
- Cookie、Authorization 和自定义头自动带入；
- GET / HEAD 做只读重放和差分实验；
- POST 等写请求只做失败快照，不自动重放；
- 请求体和响应体敏感字段脱敏；
- Trace ID 和日志模板连接研发侧；
- 观测层、归因层、结论层分开；
- 未知问题不强行匹配；
- 最终根因确认后可归档为自定义场景；
- 历史跟进、导出、重新检测和删除；
- 场景库、状态码和完整适配边界可查阅。

## 迭代中始终没有改变的原则

1. 目标请求默认只做 GET / HEAD；
2. 写请求不自动重放；
3. 模型默认关闭，规则结论不依赖模型；
4. 未知问题不强行给高置信结论；
5. 本机单用户、本地数据、回环地址访问；
6. 结果用于第一响应和研发交接，不冒充最终根因。

这些原则也解释了为什么版本很多：主要是在补“真实现场能不能用”，不是把产品扩成通用监控平台。

## 当前不覆盖

- 自动修复；
- 自动提交、删除和修改目标系统；
- 原浏览器窗口监听；
- 手机 App 和原生桌面客户端；
- WebSocket、SSE 和长连接消息；
- 系统级全流量抓包；
- 压测、故障注入和容量评估；
- 替代服务端日志、APM、数据库审计和最终人工复核。

## 最准确的产品理解

FaultDetect 的价值不是“AI 什么都能判断”，而是：

> **把一次现场故障从“用户转述”变成“可验证的请求事实和交接证据”，再用规则和可选 AI 缩小排查范围。**

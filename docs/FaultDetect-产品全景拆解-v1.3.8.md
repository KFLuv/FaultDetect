## 一、先给结论

### 1.1 产品一句话

> **FaultDetect 是一个面向非技术业务人员和客户对接人员的 Web HTTP 现场第一响应工作台：当开发、运维或技术人员无法第一时间到场时，在授权下采集真实失败请求，执行只读检测和分层归因，并输出可复核的证据与研发交接包。**

### 1.2 产品类别

它不是：

- 通用聊天机器人；
- 自动修复工具；
- 全链路 APM；
- 浏览器插件；
- 网络抓包工具；
- 压测工具；
- 能自动判断所有系统根因的“万能诊断器”。

它更接近：

> **现场第一响应工具 + HTTP 证据采集器 + 规则归因助手 + 研发交接工具。**

### 1.3 产品价值的三个层次

| 层次 | 用户得到什么 | 是否已经具备 |
| --- | --- | --- |
| 事实层 | 真实按钮触发了哪个请求，状态码、响应体、耗时和 Trace 是什么 | 已具备 |
| 归因层 | 问题更像网络、前端、后端、数据库、权限、配置还是业务 | 已具备，但属于辅助判断 |
| 行动层 | 下一步该验证什么，如何把证据交给研发 | 已具备 |
| 修复层 | 自动改配置、改代码、重试写请求或恢复业务 | 明确不做 |

## 二、用户与任务

### 2.1 主用户

- 非技术业务人员；
- 客户对接和现场支持人员；
- 客户成功、销售支持或项目协调人员；
- 开发、运维或技术人员无法第一时间到场，但需要先复现问题、拿证据并判断问题方向的人。

### 2.2 次用户

- 现场实施工程师和运维人员；
- 接手问题的开发人员；
- 需要看证据链的项目负责人；
- 需要复盘和跟进故障闭环的团队。

### 2.3 核心任务

非技术用户在故障现场最常遇到的不是“不会修”，而是：

1. 不知道先看什么；
2. 不知道该找哪个接口；
3. 不知道如何把问题准确告诉研发；
4. 只看到用户口述，没有可验证的请求证据；
5. 内部网络不允许把生产内容直接交给公网 AI。
6. 开发、运维或技术人员无法第一时间到场，现场需要先判断问题方向。

### 2.4 触发场景

- 页面点击后报错；
- 列表为空；
- 保存或提交失败；
- 登录后马上失效；
- 某个接口 401、403、404、500；
- 页面一直加载或超时；
- 测试环境正常、客户环境失败；
- 研发要求提供 URL、请求头、响应、Trace 或复现步骤；
- 业务人员只会复现，不会使用 F12。

### 2.5 不适合的用户

- 未获得目标系统授权的人；
- 需要自动修复和无人值守变更的人；
- 需要压测、容量评估、故障注入的人；
- 需要完整监控手机 App、桌面客户端或 WebSocket 长连接的人；
- 希望只输入一句话就让 AI 给出最终根因的人。

## 三、问题模型

### 3.1 根问题

> **现场故障从发生到研发接手之间，事实会丢失。**

用户口述通常是：

```text
“系统打不开”
“点保存没反应”
“客户说很慢”
```

但研发真正需要的是：

```text
哪个页面
哪个按钮
哪个请求
哪个环境
什么账号权限
请求头和 Cookie
状态码
响应体
Trace ID
是否稳定复现
```

FaultDetect 的核心价值就是把这段信息补齐。

### 3.2 现有替代方式

| 方式 | 强项 | 缺口 |
| --- | --- | --- |
| 用户口述 | 快 | 信息失真，研发无法定位 |
| F12 / DevTools | 证据准确 | 业务人员不会用，现场效率低 |
| 截图 | 直观 | 看不到完整请求、响应和 Trace |
| 通用 AI | 会解释 | 输入仍是转述，无法自己拿现场事实 |
| APM / 日志平台 | 数据完整 | 依赖接入，现场临时问题不一定有 |
| FaultDetect | 现场采集、只读检测、证据交接 | 只覆盖 Web HTTP，不替代完整监控 |

## 四、产品目标与非目标

### 4.1 产品目标

1. 让不会 F12 的非技术人员也能采集真实失败请求；
2. 让目标请求在只读边界内执行检测；
3. 让观测事实、归因推断和建议结论分层展示；
4. 让每条假设带支持证据、反证条件和验证动作；
5. 让问题能够通过 Trace、交接包和历史记录进入研发闭环；
6. 让模型不可用时，产品仍然能够输出规则结论；
7. 让用户清楚知道哪些场景支持、哪些只支持一半、哪些明确不支持。

### 4.2 非目标

- 不做自动修复；
- 不做无人值守排障；
- 不做任意写请求重放；
- 不做全量网络抓包；
- 不做性能压测；
- 不做商业 APM；
- 不做多租户 SaaS；
- 不做手机 App 和原生客户端的统一探针；
- 不承诺 132 个场景在真实企业环境全部一次命中。

## 五、产品结构

### 5.1 四个产品面

| 产品面 | 作用 |
| --- | --- |
| 采集面 | 在应用内打开业务系统，复现问题，关联按钮和请求 |
| 检测面 | 对 GET / HEAD 执行只读探测、差分实验和特征提取 |
| 归因面 | 规则、知识库和可选 LLM 生成假设、证据、反证和验证动作 |
| 闭环面 | 报告、Trace、交接包、历史、跟进、导出和场景沉淀 |

### 5.2 功能模块

| 模块 | 用户价值 |
| --- | --- |
| 故障检测 | 手动 URL 或采集请求进入诊断 |
| 内置采集 | 不需要 F12，自动拿请求与登录态 |
| 使用教学 | 内置演示、完整能力边界、全部场景目录 |
| 场景库 | 搜索和查看知识库规则 |
| 状态码 | 搜索状态码、含义和排查建议 |
| 历史记录 | 任务跟进、负责人、状态、导出和重新检测 |
| 新增场景 | 把现场新问题沉淀为自定义规则 |
| 系统自检 | 用独立实现验证观测层 |
| 模型设置 | 可选 LLM 配置和连接测试 |
| 未知场景模式 | 不强行匹配，输出现场采集清单和研发交接包 |

## 六、完整使用方法

### 6.1 使用前提

- 系统：Windows x64；
- 已获得目标系统的诊断授权；
- 优先使用测试环境；
- 生产环境优先选择只读查询操作；
- 确认当前电脑能访问目标系统；
- 不要在报告中保留未经判断的业务敏感数据；
- 不要把 FaultDetect 当作证书校验工具。

### 6.2 启动

1. 双击 `FaultDetect-1.3.8-portable.exe`；
2. 程序自动启动内置 JRE 和本地后端；
3. 主窗口打开，不需要系统浏览器；
4. 业务数据默认保存在 `%LOCALAPPDATA%\FaultDetectSystem\data`；
5. Windows 如出现 SmartScreen 提示，是因为当前包未做代码签名。

### 6.3 第一次使用：先跑教学

1. 打开左侧“使用教学”；
2. 查看“从问题页面到诊断报告”主流程；
3. 打开内置订单、账号或审批演示网站；
4. 在演示页面点击“开始记录本次问题”；
5. 点击演示页面里的失败按钮；
6. 点击“完成采集”；
7. 在候选列表中选择失败请求；
8. 确认授权并点击检测；
9. 查看诊断结果和交接包。

目标：

- 确认记录开关正常；
- 确认按钮名称与请求关联；
- 确认失败请求优先；
- 确认凭证不显示；
- 确认 POST 不自动重放。

### 6.4 标准现场采集流程

1. 进入“故障检测”；
2. 在“打开业务系统”输入首页地址；
3. 在应用内正常登录；
4. 进入能稳定复现问题的页面；
5. 不要先开始记录，先确认页面已经加载完成；
6. 点击“开始记录本次问题”；
7. 点击真正出问题的业务按钮；
8. 如需确认请求体，先打开“请求体证据”并完成确认；
9. 看到问题后点击“完成采集”；
10. 在候选列表中优先选择失败请求；
11. 核对请求的方法、域名、路径、按钮名称、状态码；
12. 确认已获得诊断授权；
13. 点击候选请求执行检测；
14. 阅读结论，按需展开完整诊断过程；
15. 复制汇报文本或研发交接包；
16. 在历史记录中记录负责人、状态和备注。

### 6.5 技术人员手动模式

适用于已有接口 URL 的场景：

1. 展开“技术人员入口”；
2. 输入接口 URL；
3. 填写故障症状；
4. 勾选已获得授权；
5. 选择是否做 TCP 服务存活检测；
6. 按需开启差分隔离实验；
7. 按需填写 Cookie、Authorization 或自定义请求头；
8. 选择超时；
9. 点击“开始检测”；
10. 查看报告并按验证动作继续复核。

手动模式不会从原浏览器自动读取 Cookie，也不会自动补登录态。

### 6.6 POST / 写请求快照流程

1. 只允许通过内置采集获取原始请求；
2. 开启记录；
3. 执行一次失败提交；
4. 完成采集；
5. 选择 POST / PUT / PATCH / DELETE 请求；
6. 不执行自动重放；
7. 查看失败快照；
8. 检查状态码、响应体、请求体、耗时和 Trace；
9. 复制交接信息给研发；
10. 允许研发在测试环境按业务规则自行复现。

产品能够做：

- 记录失败事实；
- 脱敏后提供证据；
- 给出初步问题层和下一步。

产品不能做：

- 自动再次提交；
- 自动验证业务是否真正成功；
- 自动处理一次性验证码和支付；
- 自动完成多步骤事务。

### 6.7 差分实验

差分实验是高级选项，默认关闭。开启后可能产生最多 7 次只读对照请求：

- 去掉认证头；
- 去掉自定义头；
- GET 换 HEAD；
- HTTP / HTTPS 对照；
- 追加随机参数；
- 原样只读重放。

使用条件：

- 目标系统允许重复只读请求；
- 用户已获得授权；
- 目标没有严格禁止重复请求的防护；
- 查询本身无副作用。

### 6.8 未知场景流程

当知识库没有高置信匹配时：

1. 系统进入未知场景模式；
2. 展示现场信息采集清单；
3. 按端口、服务、HTTP、鉴权、业务、数据、前端七层判断；
4. 展示已排除、怀疑和未确认项；
5. 推荐下一项只读验证；
6. 生成研发交接包；
7. 最终确认根因后，用户填写场景名称、归属、结论和解决动作；
8. 系统归档为自定义场景并生成待审核规则候选。

系统不会：

- 自动把猜测写进知识库；
- 未确认根因就自动创建高置信场景；
- 因重复提交而创建重复场景。

### 6.9 状态码与场景库

状态码页：

- 支持按状态码、名称、说明、排查建议和问题分类搜索；
- 支持按类别筛选。

场景库页：

- 支持按名称、结论和编号搜索；
- 支持按状态码过滤；
- 支持按问题归属过滤；
- 可展开查看响应特征、症状关键词和解决建议。

### 6.10 新增自定义场景

1. 进入“新增场景”；
2. 填写场景名称；
3. 填写关联状态码；
4. 选择问题归属；
5. 填写响应特征关键词和界面症状；
6. 填写结论和解决建议；
7. 使用“验证匹配”确认是否能命中；
8. 如果提示不会成为主结论，补充更强区分特征；
9. 保存场景；
10. 在教学页完整场景目录中确认新增项。

### 6.11 历史跟进

每个检测任务支持：

- 新建；
- 排查中；
- 待确认；
- 已修复；
- 已关闭；
- 负责人；
- 跟进备注；
- 关闭原因；
- JSON 导出；
- Markdown 导出；
- 重新检测；
- 单条删除；
- 清空全部历史。

关闭任务必须填写关闭原因。

### 6.12 系统自检

点击“系统自检”后：

- 用 `HttpURLConnection` 生成独立真值；
- 用产品实际 `HttpClient` 链路执行检测；
- 对比 8 条观测用例；
- 展示归因层 10 条固定事实用例。

当前严格结果：

- 观测层 `7/8`；
- 归因层 `10/10`；
- 已知差异为 DNS 失败与连接拒绝未细分。

### 6.13 LLM 增强

默认关闭。开启条件：

1. 在“模型设置”中填写 OpenAI 兼容接口；
2. 填写模型名和 API Key；
3. 测试连接；
4. 保存；
5. 单次检测时主动勾选 LLM 增强。

失败时：

- 状态变为 `degraded`；
- 原因写入结果；
- 规则结论仍然保留；
- 不阻塞主流程。

### 6.14 数据备份与清理

- 数据目录：`%LOCALAPPDATA%\FaultDetectSystem\data`；
- 历史数据库：`fault_detect.db`；
- 自定义场景：`custom_scenarios.json`；
- 规则候选：`rule_candidates.json`；
- 历史默认保留 180 天；
- 停止程序后可以备份数据目录；
- 卸载便携版可以删除 EXE 和可选数据目录；
- 采集 Session 的 Cookie 不作为持久历史保存。

## 七、如何阅读诊断结果

### 7.1 四层信息

| 层 | 回答的问题 | 可信度来源 |
| --- | --- | --- |
| 观测事实 | 实际看到了什么 | HTTP、TCP、响应体、耗时 |
| 差分结果 | 改变一个变量后有什么差异 | 受控只读对照 |
| 归因假设 | 问题最可能在哪一层 | 知识库、通用规则、差分 |
| 结论建议 | 下一步做什么 | 规则与可选模型补充 |

### 7.2 置信度怎么理解

- 高置信：事实与场景特征高度一致；
- 中置信：存在多个合理候选，需要验证；
- 低置信：进入未知场景模式，不强行下结论；
- 任何置信度都不是最终根因证明。

### 7.3 必看的三个字段

1. 支持证据：系统看到了什么；
2. 反证条件：出现什么情况说明结论不成立；
3. 验证动作：用户或研发下一项应该核对什么。

### 7.4 不建议只看的内容

- 不要只看一个百分数；
- 不要把场景名直接当最终根因；
- 不要把 HTTP 200 等同于业务成功；
- 不要把一次响应等同于稳定复现；
- 不要在没有日志和业务规则复核时声称问题已解决。

## 八、能力边界

### 8.1 能做什么

| 能力 | 当前程度 |
| --- | --- |
| 打开 Web 系统并采集请求 | 支持内置窗口内的 HTTP / HTTPS |
| 关联按钮与请求 | 支持记录期间 30 秒内的最近交互 |
| GET / HEAD 自动检测 | 完整支持 |
| POST 等方法诊断 | 只做失败快照，不重放 |
| 网络和状态码观测 | 支持 |
| 编码识别 | 支持 charset 和回退探测 |
| 请求体证据 | 用户确认后采集文本类请求体 |
| Trace ID | 常见头和 JSON 字段提取 |
| 日志平台 | 复制 Trace、应用 URL 模板 |
| 历史和跟进 | 支持 |
| 自定义场景 | 支持预检、保存和归档 |
| LLM | 可选，默认关闭 |

### 8.2 能做到什么程度

| 问题类型 | 能做到的程度 |
| --- | --- |
| 500 且有明确异常 | 可以定位到后端或数据库层，并给出日志验证动作 |
| 401 / 403 | 可以定位到认证或权限方向，并提示检查 Token、Cookie、RBAC |
| 404 | 可以区分接口路径、部署版本和网关转发方向，但未必知道具体责任人 |
| 跨域 | 可以提供 CORS 方向，但完整判断仍依赖浏览器控制台 |
| 空数据 | 可以提示检查数据库返回和前端渲染，但不能直接证明表数据一定为空 |
| POST 参数错误 | 可以采集脱敏请求体和响应，但不能自动重放确认 |
| 偶发超时 | 如果当时成功捕获到，可以保留证据；如果无法复现，不能替代长期监控 |
| 前端样式或 DOM 错误 | 能力有限，主要依赖页面现象和请求结果 |
| 业务规则错误 | 可读取业务码和提示，但无法替代业务规则文档 |
| 服务端最终根因 | 不自动确定，必须结合日志、APM、数据库和代码复核 |

### 8.3 做不了什么

- 不自动修复；
- 不自动提交写请求；
- 不监听原浏览器；
- 不支持手机 App 和原生桌面客户端；
- 不支持系统级全流量；
- 不完整支持 WebSocket / SSE；
- 不处理完整文件上传和流式内容；
- 不做压测和故障注入；
- 不做证书链验证；
- 不做 SSRF 白名单；
- 多用户和局域网协作不在当前范围；
- 不替代 APM、日志平台和数据库审计。

## 十二、AI 与规则体系

### 12.1 为什么规则优先

- 现场结果需要可复现；
- 模型输出不稳定；
- 内网可能无法访问模型；
- 生产数据可能不能外发；
- 模型不能替代 HTTP 事实和日志验证。

### 12.2 模型负责

- 对已有事实做解释；
- 补充验证动作；
- 在规则不足时提供候选思路；
- 优化表达。

### 12.3 模型不负责

- 决定请求是否成功；
- 伪造状态码和响应；
- 自动执行写操作；
- 自动修改知识库；
- 替代最终根因确认。

### 12.4 降级原则

- 非 2xx；
- 超时、DNS、证书错误；
- 解析异常；
- 非法 JSON；
- 缺少关键字段；
- 返回结构不符合预期。

以上情况全部降级为规则结论，主流程仍可完成。

### 16.1 用户价值

- 减少“让用户再复现一次”；
- 减少研发反复索要 URL、Cookie 和响应；

- 让未知问题也能形成交接包；
- 让问题可跟踪、可导出、可复盘。

### 16.2 建议指标

| 指标 | 含义 |
| --- | --- |
| 首次采集成功率 | 一次记录能否捕获正确失败请求 |
| 按钮与请求关联准确率 | 候选请求是否带对操作名称 |
| 首轮归因耗时 | 从复现到形成第一层结论 |
| 证据完整率 | 是否包含状态、响应、Trace 和复现步骤 |
| 研发可用交接率 | 研发是否能直接根据交接包继续排查 |
| 人工接管率 | 系统无法确定时必须人工处理的比例 |
| 误判率 | 结论被现场或日志推翻的比例 |
| 重复复现次数 | 引入工具前后对比 |
| 需求返工降低 | 研发因信息不足而反复追问的次数 |

### 16.3 反指标

- 不能为了提高覆盖率而伪造结论；
- 不能把知识库命中当最终根因；
- 不能为了展示 AI 而默认调用模型；
- 不能为了提高自动化程度而重放写请求；
- 不能隐藏无数据和失败状态。

## 附录 A：59 个状态码

| 状态码 | 名称 | 类别 | 下一步 |
| --- | --- | --- | --- |
| pending | 无响应 / 超时 | 无响应 | 第 0 步检查服务存活（TCP 连接测试） |
| 100 | Continue | 信息 | 确认代理/网关是否丢弃或未处理 Expect: 100-continue |
| 101 | Switching Protocols | 信息 | 检查网关是否放行 WebSocket 升级头（Upgrade / Connection） |
| 102 | Processing | 信息 | 确认网关/浏览器超时是否早于后端实际处理时间 |
| 103 | Early Hints | 信息 | 确认为性能优化提示，不影响功能正确性 |
| 200 | OK | 成功 | 分析响应数据（有数据=前端渲染问题；空数组=数据库没数据） |
| 201 | Created | 成功 | 检查前端是否处理成功响应（刷新/提示） |
| 202 | Accepted | 成功 | 检查异步任务状态 |
| 203 | Non-Authoritative Information | 成功 | 对比直连后端与经过网关的响应体差异 |
| 204 | No Content | 成功 | 检查前端是否处理成功响应 |
| 205 | Reset Content | 成功 | 前端在收到 205 后清空表单 / 重置视图 |
| 206 | Partial Content | 成功 | 核对请求 Range 与响应 Content-Range 是否匹配 |
| 226 | IM Used | 成功 | 核对增量更新基线（ETag / 版本号）是否一致 |
| 300 | Multiple Choices | 重定向 | 检查服务端多选项配置 |
| 301 | Moved Permanently | 重定向 | 修正前端 URL |
| 302 | Found | 重定向 | 检查重定向配置是否异常 |
| 303 | See Other | 重定向 | 检查前端是否跟随重定向 |
| 304 | Not Modified | 重定向 | 检查缓存策略 |
